## 1. 总目标与原则

**目标**：6~8 周内走到 **v0.2.0**——采集准确率可审计、额度卡补齐主要提供商、采集器架构可维护、皮肤包完成对齐、README 能当门面。

**原则**：

1. **采集准确性优先于新功能**——这是本项目的护城河（上游是 macOS，Windows 端数据源差异全靠自己啃）。
2. **重构必须先铺测试安全网**——D3 的拆分没有 golden test 不许动手。
3. **reporter 不默认续命**——需要你拍板（见 §6），不让它偷吃主线时间。
4. **涉及花钱的项一律 [PAID-GATE]**，标记后等你同意再动。
5. 每项任务带**验收标准**，完成必须有过验证证据（跑过什么命令、看到什么结果）。

## 6. token-eyes 对照吸收清单（2026-11-19 补）

> 应用户要求补充：把 token-eyes（`muxunson-9677/token-eyes`，MIT）与本项目逐项对照，明确"吸收什么、不吸收什么、为什么"。**只借鉴思路与公开数据，不搬运代码**；如引用其实现思路，在 CHANGELOG 致谢。

### 6.1 provider 覆盖对照（token-eyes 22 家 vs 本项目 16 家）

- **双方都支持（8 家）**：Claude Code、Codex、Cursor、Gemini CLI、OpenCode、Kimi Code、Grok Build、Antigravity。
- **本项目独有（8 家）**：CC Switch、MiniMax 双库、DSH（TokenLens 全量口径）、ZCode、WorkBuddy、Qwen Code、Amp、Droid——token-eyes 清单里没有这些。
- **token-eyes 独有（13 家）**：Kiro、OpenClaw、Every Code、GitHub Copilot、oh-my-pi、**CodeBuddy（腾讯）**、Kilo CLI、Kilo Code、pi、Craft Agents、Roo Code、Zed Agent、Goose。

**吸收判断**：不盲目追 22 家对齐。按"你自己真在用/国内生态相关/数据源可靠"三筛：优先级排序为 **CodeBuddy（腾讯，Claude-Code fork，hook 接入路径与 Claude Code 同构，成本低）→ Every Code → Copilot（OTEL 文件导出思路）→ Kiro/Zed/Goose（SQLite 被动读取，schema 参考价值高）**；OpenClaw/Kilo/pi/Craft/Roo 等小众源挂起，等真实需求。

### 6.2 成本引擎（差距最大、最值得吸收）

| | 本项目 | token-eyes |
|---|---|---|
| 定价数据 | `config/pricing.json` 小表 + `pricing.rs` 十余个硬编码 fallback（opus/sonnet/gpt-5.5/gpt-5.4） | **LiteLLM 公开数据集 `model_prices_and_context_window.json`**，seed 快照 2284 个模型 |
| 刷新机制 | 随版本发布 | 24h 磁盘缓存 + 打包 seed 兜底 + matcher 前缀/子串匹配 |

**吸收方案（T18）**：把 LiteLLM JSON 引入为定价数据源，**但做成"构建期生成"而非运行时拉取**——token-eyes 的 24h 在线刷新机制不能照搬，因为本项目 PRIVACY.md 承诺"唯一外部网络请求是检查更新"，运行时拉定价会破坏这条承诺。正确姿势：新增构建脚本定期拉 LiteLLM 最新快照 → 生成精简版 `pricing.json`（只保留 AI 编程工具相关模型）随版本发布；运行时零网络。`pricing.rs` 的 match_model 前缀匹配逻辑保留，仅换数据源。验收：MiniMax/DSH/Gemini 等此前落 default 兜底价的模型出现真实分档定价；离线安装包成本估算照常工作。

### 6.3 接入方法论

token-eyes 把 22 家分成三类：**hook 写入**（SessionEnd/notify，6 家）、**插件**（2 家）、**被动读取**（15 家）。其被动读取类各家数据源路径有直接参考价值（Kiro SQLite+JSONL 混合、Zed `threads.db` 仅计 zed.dev 模型、Goose `sessions.db` 累计量 delta、Copilot `COPILOT_OTEL_FILE_EXPORTER_PATH`）。本项目新增 provider 时（T19）按同口径分类，被动读取优先——不改用户配置、无卸载残留，与本项目隐私立场一致。

### 6.4 明确不吸收的

| token-eyes 能力 | 不吸收理由 |
|---|---|
| 云端排行榜 | 其 README 自认依赖第三方免费服务"可能不可用或过期"；本项目 scys Token 榜单（可选）已覆盖该需求，且隐私承诺不扩面 |
| 跨设备聚合 | 需要云端账号与上传，直接违背 PRIVACY.md 本地优先承诺 |
| 30 分钟 UTC 桶聚合架构 | 本项目流式聚合（Aggregator，内存与事件量解耦）已是更优解 |
| Node.js CLI 分发形态 | 技术栈不同；Windows 端 Tauri 单 exe + 自动更新体验更好，无需引入 Node 运行时 |
| 桌面小组件 ×4 | Windows Widgets 生态价值待验证；上游 macOS 的 Token Island 对应物（托盘浮层）可作为 v0.2.x 之后的远期项 |

## 7. 需要你拍板的决策项

### 决策 1：reporter 双榜单怎么办（D8）

现状：阶段 0~2 完成（4 个采集器+分类器+流式聚合），阶段 3~4 被生财 `x-gz3/x-t41` 混淆头和 zhenganhuo 设备绑定墙挡死，**8 个月没动**。两个榜单是从协议层有意封锁第三方。

| 选项 | 代价 | 产出预期 |
|---|---|---|
| A. 续命逆向（Ghidra 工具链已就绪） | L，且不确定性高——对方是**有意设计**的反第三方保护，逆向出来也可能被服务端更新再次封锁 | 榜单自动化上报 |
| B. 降级妥协：手动导出上传 | S | 半自动，解除两个独立客户端依赖 |
| C. 挂起，主线优先 | 0 | 现有 opentoken + token-rank 继续并存 |

**建议 C**：它不是这个项目的主价值（隐私承诺 PRIVACY.md 明确主程序不上传，reporter 只是 opt-in 附属），8 个月未推进本身就说明优先级低。若榜单对你重要，选 A 但**设两周 time-box**，到期未破就落 B。

### 决策 2：真证书签名 [PAID-GATE]

$100~400/年 换掉 SmartScreen「未知发布者」。7★ 的小项目期可以缓，但如果 T17 增长基建做了、有真实外部用户进来，建议买——这是转化率的第一道坎。

### 决策 3：增长投入度（T17）

做不做英文 README / demo GIF / 发布节奏化。技术之外但这直接决定 7★ 能不能涨。
